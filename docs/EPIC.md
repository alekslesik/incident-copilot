# Эпик: помощник по диагностике инцидентов на Go с LLM

## Результат

Пользователь отправляет описание сбоя и получает проверяемые гипотезы на основе учебной документации и синтетических логов. Сервис ограничивает обращения к модели и инструментам, измеряет качество и расходы, сообщает о нехватке данных.

Эпик завершён после выполнения критериев раздела 9 [ТЗ](SPEC.md). Все задачи ниже пока открыты. T01–T12 — идентификаторы задач. [Эпик на GitHub](https://github.com/alekslesik/incident-copilot/issues/1) связывает все задачи.

## Этап 1. Первый работающий вызов, недели 1–4

- [ ] **[T01. Каркас Go-сервиса](https://github.com/alekslesik/incident-copilot/issues/2).** Конфигурация, HTTP server, graceful shutdown, request ID, `/healthz`, `/readyz`, `.env.example`. Приёмка: сервис запускается локально, завершается по сигналу, отсутствие обязательной конфигурации даёт понятную ошибку. Зависимости: нет.
- [ ] **[T02. Клиент LLM](https://github.com/alekslesik/incident-copilot/issues/3).** Один провайдер за интерфейсом, deadline, обработка ошибок, учёт usage. Приёмка: успешный вызов и проверки timeout/429/5xx через stub; секреты не попадают в логи. Зависимости: T01.
- [ ] **[T03. Контракт анализа](https://github.com/alekslesik/incident-copilot/issues/4).** Синхронный `POST /v1/analyses`, JSON Schema и валидация ответа; лимит одной попытки исправления формата. Приёмка: корректный запрос возвращает гипотезы и ограничения, некорректный вывод не маскируется под успех. Зависимости: T02.
- [ ] **[T04. Датасет и baseline](https://github.com/alekslesik/incident-copilot/issues/5).** 20 сценариев с ожидаемыми фактами и рубрикой; runner, сохраняющий модель, параметры и результаты. Приёмка: получен воспроизводимый по входным данным baseline-отчёт с качеством, задержкой и токенами; вариативность модели отмечена. Зависимости: T03.

## Этап 2. Ответы по документации, недели 5–8

- [ ] **[T05. Хранилище и импорт документов](https://github.com/alekslesik/incident-copilot/issues/6).** Миграции PostgreSQL, Markdown/TXT до 1 MiB, checksum, версии и статус индексации. Приёмка: повторный импорт обрабатывается определённым образом; новая версия становится активной после успешной индексации. Зависимости: T01.
- [ ] **[T06. Retrieval](https://github.com/alekslesik/incident-copilot/issues/7).** Chunking, полнотекстовый baseline, embeddings/pgvector и сравнение поиска. Приёмка: на размеченных вопросах измерена доля найденных релевантных фрагментов; размер контекста ограничен. Зависимости: T04, T05.
- [ ] **[T07. RAG и источники](https://github.com/alekslesik/incident-copilot/issues/8).** Передача найденных фрагментов, проверка source ID, ответ при нехватке данных. Приёмка: выполнены целевые критерии качества ТЗ, приложено сравнение с baseline; корректность ссылок и смысловая поддержка оцениваются отдельно. Зависимости: T06.

## Этап 3. Инструменты и эксплуатация, недели 9–12

- [ ] **[T08. Read-only поиск логов](https://github.com/alekslesik/incident-copilot/issues/9).** Синтетический JSONL, фильтры сервиса/времени/уровня/trace ID, валидация аргументов. Приёмка: максимум 3 вызова на анализ, 100 записей на вызов, интервал до 24 часов; произвольные SQL, shell и URL недоступны. Зависимости: T07.
- [ ] **[T09. Worker и жизненный цикл заданий](https://github.com/alekslesik/incident-copilot/issues/10).** HTTP 202, GET статуса, PostgreSQL queue, lease, Idempotency-Key. Приёмка: повторная отправка возвращает тот же ID, другое тело с тем же ключом даёт 409; истёкшее задание восстанавливается без дубля сохранённого результата. Зависимости: T05, T08.
- [ ] **[T10. Бюджеты и защита](https://github.com/alekslesik/incident-copilot/issues/11).** API-токен, rate/concurrency limits, общий deadline, резервирование token/cost budget, adversarial-проверки. Приёмка: лимиты соблюдаются и при конкурентных запросах, секреты не раскрываются в подготовленных тестах, отказы понятны пользователю. Базовые ограничения добавлять уже в T02/T03; здесь завершить сквозную проверку. Зависимости: T09.
- [ ] **[T11. Метрики и диагностические логи](https://github.com/alekslesik/incident-copilot/issues/12).** `/metrics`, длительность, ошибки, очередь, токены, расходы. Приёмка: метрики отражают успешный и ошибочный сценарии, отсутствуют высококардинальные labels и тексты пользовательских данных. Зависимости: T09.
- [ ] **[T12. Упаковка и демонстрация](https://github.com/alekslesik/incident-copilot/issues/13).** Docker Compose, CI с fmt/vet/test, примеры curl, итоговый eval-отчёт и краткая запись архитектурных решений. Приёмка: чистый checkout запускается по README; показаны успешный анализ, нехватка данных и ошибка провайдера. Зависимости: T10, T11.

## Порядок старта

Начать с T01 → T02 → T03 → T04. Не добавлять broker, Kubernetes, frontend и несколько провайдеров до первого измеренного результата. T05 можно выполнять после первого вызова модели, но подключать retrieval после подготовки baseline.

## Шаблон отдельной GitHub Issue

**Название:** Txx — краткое название.

**Цель:** какой пользовательский результат даёт задача.

**Работы:** конкретные изменения.

**Приёмка:** наблюдаемый результат и значимые проверки из списка выше.

**Зависимости:** Txx.
