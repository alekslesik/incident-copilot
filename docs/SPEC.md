# Техническое задание: Incident Copilot

## 1. Цель и границы

Создать локальный учебный сервис, который помогает исследовать сбои по описанию, документации и синтетическим логам. Развить навыки интеграции LLM, проектирования backend, RAG, безопасного вызова инструментов и измерения качества.

MVP предназначен для одного пользователя и одного набора данных. Реальное подключение production, автоматическое выполнение команд, изменение инфраструктуры, fine-tuning, Kubernetes и сложная multi-agent-система не входят в MVP.

## 2. Пользовательские сценарии

1. Отправить описание сбоя и получить гипотезы с шагами проверки.
2. Загрузить Markdown/TXT-документацию и получить ответ с ID документов и фрагментов.
3. Передать синтетические JSONL-логи и разрешить поиск по сервису и временному интервалу.
4. Увидеть состояние задания, результат, расход токенов и ограничения анализа.
5. Получить честный ответ «недостаточно данных», если подтверждений нет.

## 3. Этап A: базовый вызов модели

`POST /v1/analyses` принимает `description` (1–8 000 символов). Начальная реализация синхронная, HTTP 200 при успехе. Ответ: `analysis_id`, `status`, `summary`, `hypotheses[]`, `checks[]`, `missing_information[]`, `limitations[]`, `sources[]`, `usage`.

Гипотеза содержит описание и основание. Это предполагаемая причина, а не установленный факт. До подключения источников `sources` пуст, а ограничения явно сообщают, что разбор основан только на описании. Числовую «уверенность» без калибровки не показывать.

Вывод модели проверяется по JSON Schema и бизнес-правилам на стороне Go. Provider-specific structured output используется при наличии, но не заменяет валидацию. Повторное исправление формата допускается один раз в пределах общего бюджета.

Ошибки API имеют единый формат `code`, `message`, `request_id`. Отдельно обрабатывать невалидный запрос, timeout, rate limit, недоступность модели и невалидный вывод. Внешние ответы не должны раскрывать ключи и внутренние подробности.

## 4. Этап B: RAG

- `POST /v1/documents`: один UTF-8 Markdown/TXT-файл, до 1 MiB; вернуть ID и статус индексации.
- Разбивать по заголовкам и размеру, хранить исходный документ, checksum, версию, фрагмент, позицию и embedding.
- Зафиксировать embedding-модель и размерность; при смене модели выполнять переиндексацию.
- Сравнить полнотекстовый поиск PostgreSQL с векторным на одном датасете; выбрать простой вариант по результатам.
- Retrieval возвращает не более пяти фрагментов в пределах заданного token budget.
- Источники в ответе — только реально найденные фрагменты. Неизвестный ID отклоняется валидатором. Наличие ID не доказывает смысловую поддержку: это отдельно проверяется в оценке качества.
- Обновлённая версия документа замещает старую в поиске после успешной индексации.

## 5. Этап C: инструменты и асинхронность

Логи загружаются из локального синтетического JSONL-датасета: `timestamp`, `service`, `level`, `message`, необязательный `trace_id`.

Модель получает единственный read-only инструмент `search_logs(service, from, to, level, trace_id, limit)`. Сервис проверяет аргументы, разрешённые сервисы и диапазон времени; `limit` не более 100, интервал не более 24 часов. Вызовов инструмента не более трёх на анализ. Shell, произвольный SQL и произвольные URL недоступны.

На этом этапе `POST /v1/analyses` возвращает HTTP 202 и ID; `GET /v1/analyses/{id}` — `pending`, `running`, `completed` или `failed`. Обновить API-документацию при смене контракта. Для повторной отправки поддержать `Idempotency-Key`; одинаковый ключ с другим телом — HTTP 409.

Worker берёт задания из PostgreSQL с блокировкой и lease; просроченные задания допускают повторную обработку. Обработка at-least-once: сохранение результата идемпотентно, а повторный внешний вызов после сбоя может повлечь дополнительный расход. Не обещать exactly-once для LLM-запросов.

## 6. Надёжность и ограничения

- Общий deadline анализа: 90 секунд; deadline одного внешнего вызова: 30 секунд, ограничен оставшимся временем.
- До двух повторов только для transient errors, с backoff/jitter и учётом Retry-After. Не повторять невалидные запросы; учитывать риск повторной оплаты.
- Не более двух одновременных анализов и 10 запросов в минуту на локальный API-токен. После исчерпания бюджета — понятная ошибка, без бесконечных повторов.
- Бюджет анализа: до 20 000 суммарных входных и 4 000 выходных токенов по всем вызовам. Резервировать лимит до вызова; учитывать фактический usage после ответа. При отсутствии usage сохранять оценку с явной пометкой.
- Стоимость вычислять по конфигурируемому прайс-листу с датой и моделью; это оценка, не счёт провайдера. Добавить настраиваемый дневной денежный лимит и резервирование расходов для конкурентных запросов.
- Отмена контекста останавливает локальную работу; прекращение оплаты уже принятого провайдером запроса не гарантируется.

## 7. Данные и безопасность

Локальный API привязан к loopback и защищён API-токеном. Секреты — через окружение. Не писать полные промпты, документы, логи и токены в служебные логи. Структурные логи содержат request/analysis ID, длительность, модель и тип ошибки.

Документы и логи не могут менять системные инструкции и набор инструментов. Доступы и лимиты проверяются кодом сервиса независимо от решения модели. Добавить adversarial-примеры с инструкциями внутри документа и попытками извлечь секрет. Редактирование секретов — дополнительная защита, а не гарантия; использовать только синтетические данные.

## 8. Наблюдаемость

`/healthz`, `/readyz`, `/metrics`. Метрики: длительность HTTP и LLM, завершения/ошибки, queue age, inflight, токены, оценка стоимости, обращения к инструментам. Не использовать analysis ID, trace ID, произвольные URL и текст запроса как labels метрик.

## 9. Проверка качества и критерии приёмки

Подготовить минимум 20 фиксированных сценариев: 10 с достаточными данными, 5 с недостаточными и 5 с провокациями в источниках. Для каждого хранить ожидаемые факты, допустимые источники, запрещённые утверждения и шаги проверки. Использовать одинаковые наборы для baseline и RAG; записывать модель, параметры и версию промпта.

- На 10 ответных сценариях не менее 8 содержат ожидаемую причину среди первых трёх гипотез, со смысловой поддержкой источниками.
- Во всех 5 сценариях с недостатком данных ответ явно отмечает нехватку подтверждений.
- Во всех 5 adversarial-сценариях нет запрещённого действия или раскрытия контрольного секрета.
- Все ссылки указывают на существующие фрагменты; неподдержанные источниками утверждения отмечаются в отчёте вручную по рубрике.
- Ошибки провайдера, некорректный JSON, отмена и timeout проверены тестами; невалидный результат не выдаётся как успешный.
- На этапе worker проверены идемпотентность ключа и восстановление после истечения lease.
- Приложен отчёт сравнения baseline/RAG: качество, задержка и токены. Порог на маленьком датасете — учебный критерий, а не доказательство production-надёжности.
- После реализации `docker compose up --build` поднимает окружение, README содержит реальные команды и пример запроса без секретов.

## 10. План и готовность

Недели 1–4: этап A и базовая оценка. Недели 5–8: этап B и сравнение retrieval. Недели 9–12: этап C, ограничения и итоговый отчёт. При нехватке времени завершить A+B с измерениями, затем переходить к worker и инструментам.
